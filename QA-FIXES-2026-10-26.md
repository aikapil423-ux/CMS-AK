# Website QA fixes — 26 October 2026

Developer view-as (officer ID entry) — implemented and regression checked:
- Developer Admin enters any officer ID — including the SP office — with their own signed-in session. No second login happens, no officer is signed in, and the developer is never signed out by entering or leaving an ID; sign-out stays the developer's explicit choice.
- The opened view runs under the developer's own ID: headers, profile blocks and the sign-out confirmation keep showing the Developer Admin account, with a viewing indicator naming the opened officer.
- The signed session token carries a view-as marker; every server API resolves to the viewed officer while the principal remains the Developer Admin, so screens, records, filters and permitted changes match what that officer sees and can do. Exiting restores the developer's own view.
- Entry points: the top-bar persona switcher, the role switcher modal and the users directory all enter on click; a persistent banner shows whose ID is open with a one-click return. Unknown, removed or temporarily unresolvable targets fall back to the developer's own session instead of ending it.
- Entering, switching between IDs or returning never navigates to the login page: the persona switch remounts the app tree under a switching flag that suppresses the unauthenticated redirect, so the developer moves between officer views in place.

Register visibility (complaints & FIR) — implemented and regression checked:
- MHC and SHO see every complaint and FIR of their own station; DSP sees their subdivision units, SP the whole district — nothing outside their jurisdiction.
- Enquiry/Investigating Officers and the Duty Officer see ONLY the records assigned to them — never another officer's case and never the whole station list. Assignment is the permission itself, so an assigned record stays visible even across a station boundary; unassigned records stay invisible even in their own station.
- The Duty Officer roster entry (ASI Surender Pal, eo_3) shares the officer's PNO, so SHO assignments from the EO roster resolve to the duty officer's own view.

Implemented and regression checked:
- FIR sequence uses the maximum existing sequence (including numbering gaps); current implementation supports station/year scope.
- Pending days are calculated from dates instead of frozen seed values.
- FIR create/update persists before replacing the in-memory store; a failed storage write throws instead of reporting success.
- Reports receive the current persona's district/station. Weekly and IGP inputs are district-filtered.
- Comparative rates use actual chargesheet and arrest flags, with explicit column definitions. Percentage change from a zero baseline displays N/A.
- FIR notice and builder require explicit case selection. Notice print/download/copy is disabled until a case is selected.
- Uploaded enquiry template defaults no longer invent age, incident date, appearance date or appointment time.
- Template/draft query errors propagate to visible builder errors with Retry.
- Dashboard distinguishes today's GD entries and active complaints; loading totals are not fabricated.
- Builders guard reload/close and link navigation when unsaved. Programmatic navigation and browser Back need further coverage.
- Prosecution shows discrepancies between saved snapshots and current FIR facts; historical records are not silently rewritten. New scrutiny requires a selected FIR and takes its district from that FIR.
- Demo logout persists; initial user rendering is consistent between server and client. Translator attribute metadata uses WeakMap instead of adding DOM attributes.
- GD GET no longer calls draft deletion cleanup. Other explicit cleanup paths remain.

Validation: 63 existing/new tests passed; TypeScript passed. Browser checks confirmed empty default FIR selection, matching SITREP/IGP district and calculated comparative figures. No real case was created or submitted for verification.

Deferred by user: real authentication, server API authorization and production jurisdiction/RBAC enforcement. Demo persona filtering is not a security boundary. Full hydration-error elimination, physical microphone, multi-user durability, complete PDF/print output and unsaved browser Back behavior are not certified by these checks. FIR storage remains browser-local, so cross-device uniqueness/persistence requires a server-backed implementation.
